Compatibility findings

- Existing valid packages remain valid under the proposed delta: no existing manifest, Build Plan, compiled context, runtime record or report schema is amended. NORMATIVE-DELTA.md expressly prohibits changes to existing contracts and retains static requirements even when a condition is false. This conclusion is a normative surface comparison, not an exhaustive execution of every existing package.
- Optionality is substantive. Existing Foundation and other capability claims acquire no Task Facts requirement. The proposed evaluator claim requires its complete own semantics and vectors, while expressly excluding Foundation, Compiled Runtime and integrated production conformance claims based on those vectors. This fits baseline §§4.1 and 26.
- Existing execution is unchanged unless a host invokes the optional surface. The normative text does not automatically insert an adapter into build or runtime paths. The informative integration sequence retains Scope, asOf, exact-element requirements, subject winners, failed-build behavior and ordinary runtime controls. APPLIES selects dependencies and is explicitly not permission or approval; unresolved decisions cannot grant permission.
- Exact-element requirements remain exact. The informative union of selected and static IDs is consistent with baseline §13.1; false conditions cannot erase static dependencies or turn element references into subject selectors. The candidate correctly warns that its synthetic dependency IDs do not resolve in a real manifest.
- Schema packaging is portable for the evaluator. The supplied schema passes Draft 2020-12 schema validation; all 44 `$ref` occurrences resolve to included local `$defs`, with no external payload-schema dependency. The experimental URN is explained as provenance and need not be fetched. I independently confirmed the closed roots of the baseline Model Input Package, Runtime Decision Record and build-report schemas, and the open root of the Build Plan schema. Keeping the evaluator in an external sidecar avoids incompatible field insertion.
- Canonicalization is independently implementable. TFJ specifies token restrictions, integer bounds, Unicode scalar ordering, escaping, array preservation and exact byte encoding. Its deliberate difference from governed OBDS normalization is explicit, and substitution for existing governed hashes is forbidden. Retention of conditions and verifier context addresses their separation from snapshot identity. I independently recomputed all 90 non-null snapshot-hash expectations across the supplied fixtures/regressions, with zero mismatches. This check covered those vectors, not every possible Unicode or number input.
- Routing and reasons have sufficient normative detail for implementation across languages: syntax precedes TFJ, routing precedes bound validation, family-wide routing failures suppress partial output, typed checks have an explicit order, and outcome/reason selection is deterministic. The text covers own-key lookup, booleans versus integers, complete-input validation, malformed unused facts, missing versus empty facts, partial-function association conflicts and temporal basis mismatch. Language-specific exception names apply to the described API; §8 identifies file-oriented six-field records as the normative conformance interface and permits an optional decoded API.
- Migration burden is accurately bounded. Existing adopters need no migration. Opting-in hosts must provide trusted verification context, retain exact observations/conditions/decisions and integrate selected dependencies without bypassing existing controls. Authenticity, inventory completeness, extraction, signature protocols and production integration are expressly unproven or outside scope. There is no claim that hashing establishes legal truth or entitlement.

Non-blocking finding C1 — runnable conformance packaging

CONFORMANCE-IMPACT.md contains useful literal expectations, but candidate-v1 contains no executable evaluator, regression harness or runner invocation. It packages six example families with 66 expected decisions and 24 regression input files with 36 expected records. Consequently, there are no packaged executable compatibility tests to re-run under the reviewer mandate. I did not represent the reported 102/102 implementation agreement or 57 source tests as independently re-executed results.

For subsequent official conformance packaging, include a minimal language-neutral runner contract and comparison command that preserve raw invalid input bytes, enforce the six-field comparison and exit behavior, and identify the frozen suite. This is non-blocking for this proposal because official suite registration and production integration are explicitly deferred, the normative interface is specified, and the literal vectors are already present. The external relative evidence links are usable within the ratification tree but are not a standalone distributed evidence bundle; preserve or package their referenced records when distributing the evidence claims.

Versioning assessment

MINOR is the correct class under baseline §27.1: this adds a backwards-compatible optional capability without breaking an existing normative contract. Prospective 4.1.0 from 4.0.4 is therefore justified. PATCH would understate added capability, and MAJOR is not supported by the bounded delta. Keeping snapshot payload 0.1 and TFJ-0.1 independent of capability/release numbering prevents gratuitous identity changes. Mandatory adoption, changed existing acceptance/hashes or a future wire binding must receive a fresh impact assessment.
